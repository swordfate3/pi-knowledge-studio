Embedding 是“编索引”，
不是把书存进模型脑子。

当前 Studio 源码说明 · 2026-09-07 · 本页仅演示，不调用模型，不上传资料。

三个地方，三份工作

① 本地 Studio解析书 → 文字块
原文件、图片留在本地
→
② Embedding API收到文字
返回一串数字
→
③ 本地 SQLite保存文字与数字的对应关系
记录书籍和页码

像图书馆：书留在书架上，embedding 帮每段内容生成“按意思查找的索引”。它不负责解释原文，也不负责看图片。

现在有两条入口，不要混用

普通 collection

ks_v2_import  // 只解析、保存
ks_v2_index   // 显式建立向量索引
ks_v2_search(mode="hybrid")

索引每批最多 16 个文字块。重复 index 会重新计算活动文档，不是断点续传。

默认 lexical 不调用模型；hybrid 将 BM25 与向量余弦排名用 RRF 融合。

<cwd>/.pi/knowledge-studio-v2/<collection>/

整本 PDF 任务

ks_v2_pdf_start(…, index=true)
ks_v2_pdf_resume(…, index=true)
ks_v2_pdf_search(…, mode="hybrid")

先每批最多 5 页解析整书，再每批最多 4 块 embedding。向量和进度一起保存，恢复时复用已提交批次。

默认 index 关闭；不索引会停在 parsed，目前连关键词搜索也要求先达到 ready。

<cwd>/.pi/knowledge-studio-v2-pdf-jobs/

PDF 专用搜索当前是简单的子串命中比例 + 正余弦相似度，不是普通 collection 的 BM25 + RRF。两套存储和搜索尚未统一。

你的 943 页书，实际做了什么？

1,007 × 512

1,007 个文字块，每块一个 512 维向量。

366 次

文档 embedding 串行请求；不同解析窗口不会强行凑成满批。

实际使用 tencent/WeMM-Embedding-4B；不是向 GPT 发送整本 PDF。图片单独保存，不进入这条文字 embedding 请求。

随后搜索只发送问题文字，取得一个查询向量；在本地比较已有的文档向量，不重算整本书。

这次实验的真实数据保存在私有的本地实验目录中，不随仓库发布。下列路径仅为示意：

<private-experiment-dir>/jobs/

模型不是扩展的默认值，而是实验显式配置的。实验库尚未自动接入正式工具目录；当前会话也未提供 ks_v2_* 工具。

使用你自己的 GPT，分工是这样

你的问题
   ↓
GPT 决定查什么 → 搜索工具 → 问题 embedding
                                 ↓
                       本地找回文字与来源
                                 ↓
                       GPT 阅读、继续查找、回答

图片读取、图片真正送到 GPT、原图导出是另外的功能；新 PDF 任务入口尚未接齐，不能仅凭“存了图片”就说整条看图链路已经完成。

两件必须配置好的事

模型身份一致：入库与查询匹配 provider、协议、接口、模型、版本、维度和前缀指令。不能把不同模型的数字直接混用；目前连 endpoint 变化也会影响匹配。

文字外发授权：扩展没有默认 embedding 模型。宿主配置 PI_KS_V2_EMBED_*，交互确认后才发送文档块或查询；不会自动沿用聊天模型。环境配置在扩展注册时快照保存，修改后需要重新加载才生效。

WeMM 请求：{texts, dimension}；OpenAI 兼容请求：{model, input}。API key 只用于认证，不是向量的一部分。
